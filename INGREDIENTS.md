# Build ingredients

This repository builds and packages natively on Mac OS X 10.9, and cross-builds on a modern Mac in CI (see CI, below). It has not published a release yet.

`.github/workflows/repackage-on-ingredient-bump.yml` dispatches a `-mavericks.N+1` repackage when the Rust, clang22 or make pin moves on `main`, unless the upstream pin `components/wezterm/version` moved with it, which makes the push a new upstream release. Longboat builds nothing shipped, and `components/clang22/linux-sha256` only fetches clang22's Mach-O readers on Linux, so neither repackages.

The shared preset groups every Mavergreen release (Rust, clang22, make, Longboat) into one Renovate PR, and a green build merges it.

### The pins bot

Renovate moves `DIGEST` in `components/wezterm/version`, but the build also verifies what follows from that commit: `SHA256` of the tarball `build/prepare.sh` fetches (GitHub's tarball of the commit, through shipyard's `fetch_pinned_source.sh`), `COMMITTED`, each submodule's `_DIGEST` (its gitlink at that commit) and `_SHA256`, and `components/wezterm/gitlinks.json`. Renovate cannot compute those. `.github/workflows/pins-bot.yml` runs on every push to a `renovate/**` branch whose `DIGEST` moved. Its `pins` job, which can only read, runs `scripts/pin-source-tarballs.sh --fill`. That script downloads each tarball and checks with git that it holds exactly its commit's tree, running nothing it fetched. Its `push` job never sees upstream's bytes. It writes the checked values with `scripts/pins-bot.sh apply` and pushes them as the `mavergreen-pins-bot` GitHub App, so the build runs on the new head. `gitIgnoredAuthors` in `.github/renovate.json` keeps that commit from counting as an edit to Renovate's branch. If the bot fails, run `sh scripts/pin-source-tarballs.sh --fill` on the branch (it needs git and python3) and push what it writes. `--check` writes nothing and exits 3 when the pin is stale.

Upstream licensing/attribution remains in the verified source tree. The local bundle stages upstream's existing terminal.icns, LICENSE.md, shell integration/completion and compiled terminfo; no application icon is generated or replaced. The icon is upstream's `assets/macos/WezTerm.app/Contents/Resources/terminal.icns`, which `assets/icon/update.sh` generates from `assets/icon/wezterm-icon.svg` (its metadata names Wez Furlong as creator). It is part of the repository that upstream's MIT `LICENSE.md` covers, which carries no separate notice for the artwork. The app ships that LICENSE.md in `Contents/Resources`. Complete dependency-license redistribution and packaging review remain required before a release.

The local acceptance record binds prepared input provenance, executable/staged Contents hashes and actual GUI evidence. A separate empty-target source-snapshot build and GUI replay have also passed. These local results do not replace modern-host parity or automated installed-product publication checks.

## Build tools

The build runs these family products, each pinned to one release. `build/environment.sh` first runs `build/tools.sh check`, which refuses unless each product's installed manifest (`/usr/local/mavergreen/<short>/mavergreen.plist`, key `version`) equals its pin, naming the product, the pin and what is installed. It then takes every tool from that product's own tree (`/usr/local/mavergreen/<short>/bin`), never the link farm, so the pinned product is the one used whichever member of its group is selected. Preparation (`build/prepare.sh`) needs only cargo, for `cargo fetch --locked` and `cargo update --offline`, whose output is the prepared lock; it checks the rust pin alone with `build/tools.sh tree rust` and runs that tree's cargo. `MAVERGREEN_TOOL_ROOT` moves the root both look under. A release's native and cross products share one pin, as fetch_clang22.sh expects of `components/clang22`: a native build checks `rust`, `clang22` and `make`, a cross build `rust-cross`, `clang22-cross` and `make`.

Natively, install each pinned release's pkg from its GitHub release after checking it against that release's `SHA256SUMS`: `sudo installer -pkg <pkg> -target /`. The clang22 pkgs since `22.1.8-mavericks.12` require Longboat's 10.9 SDK, so run `sudo longboat sdk install 10.9` first. Their assets are named `mavericks-clang-22-native-<tag>.pkg` and `mavericks-clang-22-cross-<tag>.pkg`, not `<short>-<tag>.pkg`.

Not pinned: `shipyard-cmake` and the shipyard scripts are the shared facility that moves with `@v1`; the build exports `CMAKE` but nothing in it runs CMake. `perl` (OpenSSL's `Configure`) is the first `perl` on `PATH`, the system's `/usr/bin/perl` on 10.9 and on a CI runner. In a cross build, the host side (build scripts and proc macros, which run during the build and never ship) compiles and links with the runner's `/usr/bin/clang` and its own SDK: `build/environment.sh --mode cross` sets `CC`/`CXX` and the cargo linker for the host triple to it, and sets `SDKROOT` only inside the 10.9 target compiler wrappers. libssh2-sys's build script runs `git submodule update --init` once and ignores its result; the vendored sources are already present.

## The Sparkle updater

`CMakeLists.txt` is the Sparkle updater, `wezterm-updater.app`. Its identity comes from shipyard's registry line for `wezterm`: bundle id `dev.mavergreen.wezterm.updater` and the feed `https://github.com/Mavergreen/wezterm/releases/latest/download/wezterm.xml`. `build/build-updater.sh` builds it with the clang22 release `components/clang22` pins, through shipyard's `fetch_clang22.sh`, with `RequireAppleClang` off and the documented OBJC flags. It is built for x86_64 at 10.9 only, because the product ships no arm64 slice. Its icon is upstream's `terminal.icns` from the verified prepared source (see above), so configuring before `build/prepare.sh` fails, naming it. Its version is the prepared snapshot version. Its public key is the family's, in `updater/ed25519_key.pub`. `tests/updater.sh` checks the identity, version and icon. It also checks that the updater links only the system and Sparkle, never the product it updates, and that it passes the compat guard. `CMakePresets.json` offers `native` and `cross` presets on shipyard's for configuring it by hand with the installed pinned clang22.

Shipyard 1.0.677 and later carry the `wezterm` registry line. With an older shipyard, `tests/updater.sh` exits 77, naming the shipyard it found.

## Commands on PATH

The pkg installs the app as `/Applications/Mavericks WezTerm.app` and the tree `/usr/local/mavergreen/wezterm`, whose `bin/` holds `wezterm`, `wezterm-gui`, `wezterm-mux-server` and `strip-ansi-escapes`; the `mavergreen` helper links them into `/usr/local/mavergreen/bin`. Each is a two-line sh wrapper that `exec`s the app's own `Contents/MacOS/<tool>` by absolute path, not a symlink. Upstream finds `wezterm-gui` (for `wezterm start`) and `wezterm-mux-server` (when `wezterm cli` starts a server) beside the path the CLI was started by, as `current_exe()` reports it, without resolving symlinks. Measured on 10.9 with the release `wezterm` started through a farm-style chain of symlinks from an unrelated directory: `start` tried to exec `…/bin/wezterm-gui` and `cli list` tried to spawn `…/bin/wezterm-mux-server`, both beside the link, and both failed. Through a wrapper both reached the app's copies. `build/package-pkg.sh` builds the pkg through shipyard's `stage_product.sh`, `build_component_pkg.sh` and `set_install_floor.sh`; `tests/package.sh` reads it back with stevedore and `artifact-facts.sh` and runs artifact conformance on the staged product's pkg. Packaging, like the updater, needs shipyard 1.0.677 or later, whose registry has `wezterm`; with an older one `tests/package.sh` exits 77.

## On-target acceptance

`build/check-release-on-10.9.sh VERSION` installs `dist/wezterm-VERSION.pkg` on Mac OS X 10.9 after checking it against `dist/SHA256SUMS`, and checks the installed product without a GUI session: the manifest and app carry VERSION, `mavergreen check` passes, each command on PATH runs from a login shell with no `LANG` and prints its usage for `--help`, `wezterm ls-fonts` run from `/` with no `LANG` reaches the app's `wezterm-gui` through the PATH wrapper (PORT.md "Locale without LANG"), `infocmp` and `tput` read the app's `wezterm` terminfo entry through `TERMINFO_DIRS`, a shell that `wezterm record` runs in a PTY (through `script`) prints a nonce and sees a UTF-8 `LANG` though `wezterm` was started with none, a mux server runs `tests/fixtures/mux-echo.sh` and answers a nonce sent through `wezterm cli`, and every server stops on SIGTERM. For TLS it makes a CA, a server certificate for `localhost` and a client certificate whose CN is the user, which is what the mux server requires, with 10.9's own `openssl` and `tests/fixtures/tls.cnf`. A second mux server then reaches the first through a TLS client domain and passes the nonce, and refuses a server signed by another CA and a host name the certificate does not carry (`tests/fixtures/mux.lua`). For SSH it starts a private, unprivileged `/usr/sbin/sshd` on 127.0.0.1 and a free port, with a fresh host key, client keys, `authorized_keys`, config, pid file and log in its own temporary directory, so neither `~/.ssh`, the system's sshd nor the user's agent takes part. A third mux server has SSH domains for it without a remote mux, each naming its own identity file and `known_hosts`, with `ssh_backend = "LibSsh"` and with `"Ssh2"`, so both the vendored libssh and libssh2 run. With each backend the nonce comes back, WezTerm says which backend it used, and sshd's log names that client (`libssh_…` or `libssh2_…`). Each backend refuses a host key other than the one in `known_hosts` before it offers a key, and fails with a client key sshd does not authorize. Without a GUI a refusal shows only in the pane: libssh prints `Host key verification failed` or `PUBLIC_KEY: Denied`; libssh2 prints the first, but for an unauthorized key asks for that key's passphrase and waits, though the key has none. A host missing from `known_hosts` would likewise wait for an answer to whether to trust it, so the check writes `known_hosts` first. Once the mux server stops, sshd must have no session left and stop on SIGTERM. Only Mavergreen's OpenSSH 10.6 sshd has run it; 10.9's own sshd has not. `--repo-tests` then runs the suite with shipyard's `run-repo-tests.sh`. It leaves WezTerm installed. `tests/release_check.sh` runs it against the staged product's pkg installed into a scratch volume, and shows it failing on a wrong SHA256SUMS line (without installing), a version the pkg is not, a `wezterm` killed when it hands `ls-fonts` to `wezterm-gui` with no `LANG`, a command that runs the wrong executable (its version and its `--help`) or is missing from PATH, a `wezterm` started through a symlink with no `wezterm-gui` beside it, an app without its terminfo, a `wezterm` that hands its `record` child `LANG=C`, a fixture shell that never answers (over the mux and over SSH), one that kills its server, a TLS domain that accepts an untrusted server and SSH domains whose unauthorized key sshd accepts; no sshd the check starts may outlive it.

## CI

`.github/workflows/release.yml` runs on every push to `main`, every pull request and a dispatch. Only `build` needs macOS (see the `macos-runner` deviation below); every other job runs on Linux.

- `ver` derives `UPSTREAM_VERSION` from the pin, resolves the version and whether this run publishes, and refuses a snapshot older than the previous release's (`build/check-snapshot-order.sh`).
- `build` (macos-26, arm64) installs the pinned Longboat and its 10.9 SDK, then clang22-cross, rust-cross and make, each verified against its release's `SHA256SUMS`. It cross-builds and stages the app (`build/build-cross.sh`), runs the compat guard (`build/check-compat.sh`), builds the updater, and runs the suite serially, since the tests share the build root's target and stage. It hands the staged app and updater to `collect`, and upstream's packed test binaries to `vm-test`.
- `collect` (Linux) packages through shipyard's stevedore seams (`build/package-pkg.sh`), writes the notes and the declared state, signs on a publishing run or writes a stand-in feed otherwise, and runs artifact conformance with clang22's Linux Mach-O readers.
- `vm-test` (Linux, Mac OS X 10.9 in `Mavergreen/mavericks-vm`) installs the run's pkg and runs `build/check-release-on-10.9.sh --repo-tests` and upstream's packed test binaries. Neither has a skip path, so anything that cannot run there fails; inside the check, `run-repo-tests.sh` keeps 77 as a skip.
- `scan`, `publish` and `retry` are shipyard's; `required (release)` is the one check branch protection requires.

No step runs x86_64 code on the arm64 runner, so nothing is translated by Rosetta. A test that executes x86_64 code runs its structural part in `build` and exits 77 at its first x86_64 execution (`tests/support/host.sh`). `run-repo-tests.sh` reports that as a skip, and `--strict-host` would not change that, because those tests declare themselves macOS-only. Their executions need the build root (the prepared source and the pinned rust and clang22), which the 10.9 guest does not have, so in the guest they skip too. Where each x86_64 execution runs:

## Version form

The version is `YYYYMMDD.HHMMSS-mavericks.N`, for example `20261026.072628-mavericks.1`, and its comparison key is `20261026.072628.1`. The upstream part is the pinned commit's UTC committer time, which `build/derive-upstream-version.sh` copies from `COMMITTED` in `components/wezterm/version` into the gitignored `UPSTREAM_VERSION`. This deviates from ed25519's date-only form on purpose: weekly snapshots of upstream `main` can share a day, and a date alone would give two different commits one version. A native 10.9 build has no git to read the time from the commit, so `COMMITTED` is recorded in the pin beside `SHA256`, taken from the commit itself. `build/check-snapshot-order.sh` (CI only) refuses a `COMMITTED` older than the previous release's, or equal to it with a different `DIGEST`.

- upstream: components/wezterm/version

## Conformance deviations

- macos-runner:release.yml:build: the cross build needs rust-cross and clang22-cross, which the family ships only for macOS, and with them the 10.9 SDK through Longboat; the updater configures with shipyard-cmake, which install@v1 installs only on macOS; and the tests that compile and read Mach-O fixtures use the same toolchain. Exit: Linux-hosted rust-cross and clang22-cross, after which the build, the updater and those tests run on Linux.
- on-target:build-root-tests: the x86_64 executions in the right-hand column of the table under "CI" need the build root, which only the build host has, and the arm64 build job stops each at its first x86_64 execution rather than run it under Rosetta: the libssh byte-order, Cocoa-availability and SecureTransport probes, the mux server's daemonizing child and `record`'s drain after the child exits, `build/check-local.sh --non-gui`, the per-package builds of the `window`, `wezterm-toast-notification` and `wezterm-gui` tests, the doctests, and the failure cases of upstream-tests.py's runner and of the release check. They run natively, in full, on a 10.9 box; everything that checks the installed product runs in vm-test through the release check. Exit: the build job compiles those probes and test binaries and hands them to vm-test beside upstream's, so the guest runs them.
- on-target:gui: the mavericks-vm guest has no logged-in Aqua session, so the GUI is not exercised in CI, and vm-test excludes the tests in `tests/upstream-exclusions-headless`, which need a WindowServer connection; exit: an on-target GUI smoke that launches the app, reads its rendered pixels, injects keys, resizes it and sees it exit cleanly, once mavericks-vm guarantees a GUI session.
- version-form: the version is `YYYYMMDD.HHMMSS-mavericks.N`, upstream's commit time to the second, not the family's date-only form for a commit-pinned port, because weekly snapshots of upstream `main` can share a day (see "Version form"); exit: none while the product follows upstream `main`; it ends if the product follows upstream's tagged releases instead.
